## 引子：一屋子对着麦克风窃窃私语的人

《The Information》的记者走进 Basis 办公室时，看到的是一群人对着麦克风低声呢喃。

这不是什么行为艺术。Basis 做的是会计领域的 AI agent，它的 agent 可以连续自主运行数小时甚至数天，端到端完成一整份报税表。而联合创始人 Mitch Troyanovsky 说，他给所有人的第一条建议是：**给 AI 尽可能多的上下文，因为它按定义永远缺上下文。**

说话比打字快得多。而当你试图把想法写下来时，你实际在做的是**把脑子里那一堆乱七八糟的念头压缩成摘要**——这才是写字慢的真正原因。这种压缩对人类是必要的礼貌：没人愿意收到一条语无伦次的 Slack 长消息。但对 agent 不是。agent 不介意，甚至更喜欢原始的、未经压缩的版本。

于是他们买了能捕捉极轻声音的麦克风，全公司——不只是工程师——都对着它们把想法完整倒出来。新人入职时觉得这场景很怪，一个月后再也回不去了。

这个细节值得放在开头，因为它是整套方法论的缩影：**当协作对象从人变成 agent 时，很多为人类优化的习惯需要被重新审视。**

## 一、被误读的编程神话

几乎所有人都同意，编程是第一个被 agent 真正攻克的领域。大部分人给出的解释是"可验证奖励"——代码要么通过测试，要么不通过，因此可以规模化地训练。

Mitch 认为这个解释只对了一部分，而且不是最重要的那部分。

**第一，编程是在运行时可验证的。** 这一点被严重低估。agent 需要信号来知道自己干得怎么样。设想一个工程师写完代码永远不能运行它——哪怕是世界上最好的工程师，也总会在某处写出一个语法错误。编程的反馈不仅存在，而且**廉价、纯文本、随处可得**：你在自己的笔记本上就能跑。

**第二，是数据，不是奖励。** 一年半前的编程 agent 已经能实现你交代的功能，但它们没有品味——不知道什么是好软件。你可以让它通过世界上所有的单元测试，这既不代表应用架子搭对了，也不代表数据库设计合理，更不代表文件拆分得当。**编程终究是主观的，是一门手艺，而手艺没法靠可验证奖励解决。**真正让 agent 从"会写代码"走向"会做工程"的，是各大实验室在预训练和后训练里堆进去的海量高质量代码数据——实验室里全是工程师，这件事天然是他们的第一优先级。

可验证奖励只是让这一切得以开始的起点，其余部分的贡献同样大，甚至更大。

这个判断很重要，因为它决定了你把编程的成功往其他领域迁移时，该迁移什么。

## 二、记忆碎片：LLM 的根本缺陷

要理解长时程 agent 为什么难，先要理解 Mitch 反复强调的那句话：

> **LLM 拥有巨大的工作记忆，但默认没有任何短期记忆和长期记忆。**

他用诺兰的《记忆碎片》做类比。电影主角患有短期记忆丧失症，每天醒来他知道自己是谁、知道一些基础常识，但完全不知道过去几年发生了什么。要朝任何目标推进——无论是买菜还是复仇——他必须给自己写字条，第二天醒来读自己的笔记，靠这个方式一点点累积认知。

这正是 agent 在超出上下文窗口之后的处境。

所以 2022 年那篇 ReAct 论文提出的"推理 + 行动"框架，在今天依然成立，但需要延伸一层。**除了"该走哪条路"的推理之外，还有一层推理是：我如何确保我的下一次推理步骤拿到了它需要的东西。**短时程任务里这不成问题，一切都在上下文窗口内。一旦跨过窗口，或者进入上下文腐化（context rot）的区间，你就必须用推理去暴力地组织自己的环境——拆子 agent、做压缩、给未来的自己留笔记。

而"给未来的自己留笔记"这件事，需要一种对自己的**心智理论**：我明天醒来会读到这张字条，什么样的写法信息密度最高、最不会被误解？

这是极其反人类的能力。人类不需要它——我们的大脑替我们做完了。而 agent 必须显式地做，并且正在被专门训练去做。

顺带回答了另一个问题：2023 年的 BabyAGI 为什么失败。当时的模型上下文窗口太小，装不下用于组织自身环境的内容；就算窗口变大了，模型在两万 token 之后的注意力质量也已崩坏；更根本的是它们不是好的推理者——**不会推理就没有自我觉察，没有自我觉察就无法自愈，错误于是层层复利。**

## 三、三次跃迁，以及之后的平静

Mitch 眼中真正称得上范式转移的时刻只有三个：

**Opus 3。** 他认为这个模型被严重低估。在它之前，你往 GPT-4 Turbo 里塞八万 token，模型是读不懂的。Opus 3 是第一个真正**读懂**长上下文的模型，这非同小可。

**o1。** 所有人都在谈的那次。

**o3。** 它证明了不只是推理的**数量**可以在推理时扩展，通过更好的训练、更多算力、更优数据，推理的**质量**本身也能提升——每一个推理 token 都更值钱。这在 o1 出来时并不显然。

推理模型为什么对 agent 是决定性的？因为它让模型能够**按需分配算力**。一条轨迹里有些决策极难，有些极其简单，你不可能用一个巨大昂贵的模型在每一步都全力开火。而当模型能把简单步骤和困难步骤的算力差异拉开几个量级时，一个副产品出现了：它在每一步都会停下来思考，因此更擅长自愈，而不是纯凭直觉一路生成到底。

然后是那句可能最反直觉的判断：

> **o3 之后没有任何范式级的变化。**

推特上每天都在刷新，中国的实验室每天都在发布，很容易觉得世界在剧烈晃动。但如果你对底层原理有扎实理解，就会发现**这些变化其实都在同一个范式之内**。他甚至说，看论文、追前沿、跟研究员聊天，这些都不是建立直觉的最好方式——很多人在这上面过度投入了。

那什么才是？**在自己的工作里大量地用它们。**当一个 agent 没有按你想要的方式实现某个功能时，追问：真正的限制因素是什么？它是不够聪明吗？大概率不是，它们已经聪明很久了。他在面试中观察到，agent 直觉最好的那批人，除了 ML 背景之外，另一大来源是**那些特别擅长把自己的工作自动化的人**——他们不只是琢磨怎么写提示词，而是琢磨怎么构建一个系统。

## 四、当验证变得昂贵

Basis 选择会计，一个漂亮的巧合是：会计本身就是一件极有意思的事。

现实世界里发生着海量的经济活动——有人从这家工厂进货、有人决定开一家新店、有人签了合同、有人交付了库存。现代资本主义的运转依赖于无数角色对这些事件做判断：CEO、税务局、放贷的银行、投资人。他们都关心真实世界，但真实世界过于庞大、过于非结构化，无法直接理解。

**会计是把这一切压缩成结构化信息、从而使人能够理解和决策的技艺。**某种意义上，它是一种关于整个经济体的智能，因为它本质是一项压缩活动。

而这个领域给 agent 出了三道编程领域没有的难题。

**运行时无法验证。** 报税表不会"编译失败"。你能得到的最终反馈是"有没有被起诉"——这个反馈回路显然太长了。

**数据极度稀缺。** 假设你拥有全国所有的真实报税表（出于隐私原因你不可能拥有），数量级相比合成数学题依然渺小得可笑。而合成也很难：**你要合成的不是文本，是必须真实且多样的产物**——于是数据多样性那一整套难题原样回来了。Mitch 相信这个问题终会被解决，只是今天没有。

**反馈回路极长。** 一份复杂的 1065 表，人类需要 20 小时以上的**净坐下来工作**时间，复杂的还更久。你可能面对五百到一千份文档，需要相互交叉映射、判断哪些重要、逐份做研究、汇总进一堆 Excel 工作簿。折算成推理步骤，轻松上千；如果算上子 agent 分叉，还要更多；如果再叠加"派五个子 agent 投票解一道极难的税务题"这类推理时算力手段，数字继续膨胀。

三重困境叠加，结论就出来了：**你没法靠跑结果来迭代。**

## 五、100 条 eval 全过，然后呢

这是全篇最锋利的一段。

假设你有一条数千步的轨迹，你写了 100 条 eval，有的是完全确定性的数值比对，有的是 LLM-as-a-judge 打分。全部通过。

**你有信心它能泛化到生产环境吗？**

Basis 的答案是：没有。

就像一个工程师告诉你"我的单元测试和端到端测试全过了"——这并不说明他把数据库架构设计对了。**有太多方式可以在过程不正确的情况下拿到正确的结果。**

他举的例子极其具体：你问 agent 一个税务问题，它完全可能答对——从预训练知识里想起来的，或者读了某篇博客。但真正的会计师不会认可这个答案，**他们要求你引用一手来源**。

> 哪怕它 100 次里对了 100 次，如果一个人只是靠查维基百科得到答案，会计师事务所不会雇他，那也就不该雇我们。

于是路径清楚了：**回到人类组织的经验里去。**

会计这个行业存在了几百年，它早就演化出了分步验证、独立复核、可确定性核对的一整套流程。有些检查对会计师是常识——试算平衡表加总是否为零、Excel 里有没有报错、这个页签是不是被误删了、这个数字有没有标注来源。这些都能被编码成验证器，有的确定性，有的交给 judge。

"苦涩教训"的信徒会说：别管这些，让 agent 在运行时自己发明一套全新的报税方法，它终将超越人类几百年积累的流程。Mitch 的回应是：**也许有一天会，但不会很快。**而在那天到来之前，你得先把活干了。

这里有一个他反复回到的洞察，我认为是整期最有迁移价值的一句：

> **人类早就习惯了和非确定性系统协作，只不过那些系统通常是他们的同事，而不是他们的电脑。**公司和流程的全部意义，就是设计一套让非确定性主体协同解决问题的系统。一旦意识到这一点，这本身就是 agent 设计。

## 六、Behavior Spec：把过程写下来

这个概念的雏形来自联合创始人 Matt，**两年前**就有了，当时内部叫"元行为"（meta behaviors）——因为它定义的不是某一次的行为，而是横跨所有轨迹的那一层行为。后来简化成了 behaviors。

**它是什么：** 一个 markdown 文件，写下你期望 agent 表现出的行为。粒度可粗可细。可以是"必须核对一手来源"，也可以更具体地指向某个特定来源；可以是"生成 PPT 后、交付前，先渲染成图片检查排版"。

**它同时是规格（spec）和评分标准（rubric）。**有人问这不就是 rubric 吗——是，但不只是。它不仅用来给 agent 打分，**更用来对齐人**。因为"agent 应该怎么表现"根本上是一个主观问题，团队内部需要一份共同承认的东西来讨论它。这一点被严重低估。

**三个决定性的设计约束：**

**第一，规范永远不给 agent 看。**这是它区别于提示词的根本。主持人当场提出了一个尖锐的问题：如果你写死"去 IRS 网站"，两年后信息换了位置怎么办？答案是——**agent 从来没有被告知要去 IRS 网站。**规范说的是"我要在这件事上给你打分"，而不是"你照这个做"。作为 agent 工程师，你决定要多具体；而**通常越不具体越好**，给原则、给理由、给上下文，让它自己想办法，这是所有擅长构建 agent 的人都懂的道理。

**第二，必须保持稀疏。**写下一条规范是**昂贵**的——你从此要维护一份状态，还可能与运行时上下文形成重复状态。所以正确做法不是把报税的所有最佳实践都记下来然后逐条检查，而是**只挑那几条你认为最重要、对生产泛化性最强、影响最大的**。其余的一概不写。

**第三，冲突时以规范为准。**当规范和运行时实现打架时，改实现，不改规范。这条保证了它不会退化成又一份没人维护的过期文档。

**判定只有三档：true / false / na。**触发条件没出现判 na，触发了且做到判 true，触发了没做到判 false。之所以要这么粗，是因为判定要跑在生产流量上，必须廉价且一眼可读。

值得一提的是负责判定的 judge 本身也是个 agent——它得读整条轨迹，得知道去哪儿看，得搞清楚自己在判哪一层（一个七层深的子 agent 体系里，你判的是根 agent 还是某个子节点）。这很贵，所以目前还跑不满全量生产流量。如何更好地标注和切分轨迹、只把相关片段喂给 judge，是这个方向上最明确的待解问题。

**谁来写？**会计师和 ML 研究员一起。Basis 甚至有一个叫"会计产品运营"的团队，专职和研究团队一起构建结果 rubric 和行为规范。因为你要写的不只是"该去查权威来源"，还包括"这类研究应该派一个带完整历史的子 agent 去做，因为它需要累积那部分上下文"——**你得同时懂专业上什么叫做对了，和怎么把它翻译成 agent 的机制语言。**

这套东西现在已经和 Braintrust 一起开源了，起因是 Mitch 和 Braintrust CEO Ankur 喝咖啡时随口讲起，对方兴奋起来。开源仓库里有规范格式、示例规范、示例 judge。Mitch 说他更希望大家采纳的不是格式，而是那个心态：

> **不要把一个运行了十小时的 agent 当成黑箱。它不是。它有大量、大量、大量的数据。如果你不去理解它是怎么干活的，你大概率对不起你的客户。**

最后一条，也是最容易被做反的一条：**规范要退休。**模型变强之后，某些行为不再需要额外约束就能稳定做到，此时应该删掉那条规范。**规范总量应该随时间下降**，活下来的越来越偏判断力、越来越少讲机械操作。一个只增不减的规范库，是老化的信号。

## 七、Context 是运行时训练数据

Mitch 认为大多数人对"提示词"的心智模型是错的。人们以为那是"用英文告诉模型该做什么"。

他的框架是：**把 context 当成训练数据，只不过你是在运行时训练这个模型。**

因为模型在推理时学习，这份"训练数据"的总量比后训练数据低好几个量级——正因如此，**它的质量要求高得多**。你要做的是确保这批数据足够高质量，从而让 agent 表现出你想要的行为。

由此引出了他对整个行业最不客气的一段批评：

> 你会看到有人为一个抽象得不好的代码文件抓狂，而他们的 context 却是一团垃圾。荒谬的是，**context 会影响运行时性能，代码的组织方式不会。**工程师把代码看得比英文金贵，可实际上英文才更金贵——英文影响性能，代码（在逻辑等价的前提下）不影响。

**本体（ontology）是这件事的下一层。**

编程 agent 有一个特点：它控制自己的 harness、工具和内置行为，但**它不控制自己的运行时训练数据**——那份数据是你的代码仓库。所以同一个 Codex，在一个仓库里表现平平，在另一个仓库里表现惊艳，差别在于后者有更好的运行时训练数据：清晰的约定、没有自相矛盾的说明、好的 skills。**代码库的本体设计，过去对工程师重要，现在对 agent 更重要。**

而非编程 agent 更进一步：**运行时训练数据是你自己拥有的。**这既是负担也是机会。

本体是什么？最简单的理解就是一个文件系统（通常是虚拟文件系统），带上元数据、节点关系、嵌入向量等等。但**本体不只是文件夹结构，还包括语言本身——有哪些对象、哪些概念**。因为如果模型是在运行时被训练的，你必须确保概念之间不混淆、整体自洽。这就是他说的"定义世界"：定义 agent 在探索周遭时，能预期看到什么。

当 agent 从运行几小时变成运行数月，这件事的量级会变。几小时的 agent 给自己留几条笔记；数月的 agent 留下的是**一整套文件夹**——那是它全部的"人生经历"。一个新启动的、上下文被高度压缩过的 agent，必须靠这套本体重新回到那个心境里去。本体设计得好不好，直接决定它能不能做到。

**对内部使用的 agent，关键问题变成了：什么是正典（canon）？**

一个新人加入公司，可以去把所有销售录音听一遍，但那不会告诉他**现在**的销售策略是什么。人类靠和同事聊天补上这一课，agent 补不上。更麻烦的是，如果你想要真正的组织智能，你不能让 agent 从这个人这儿听一套、从那个人那儿听另一套。**必须有唯一的权威来源。**

所以他说，内部文档必须像代码库一样对待——**删掉一个关键段落，就像删掉一行代码一样，会把 agent 弄坏。**对未来真正 agent 原生的公司来说，弄清楚"我们公司的正典是什么"、把它组织进一套合理的本体、并且像维护代码一样持续维护它，会成为最重要的事情之一。

## 八、不要 Move 37

主持人提了一个所有人都会提的质疑：你们用人工定义的流程去约束 agent，是不是就永远等不到那个 Move 37 了——那个人类想不到、但其实更优的解法？

Mitch 的回答分两层。

第一层是技术上的：正因为规范只挑最重要的几条写，**大部分空间依然留给了 agent 自由发挥**，理论上 Move 37 仍有余地。

第二层才是真正的答案，也是我认为整期最值得反复读的一段：

> 想象一个工程师跑来跟你说："这是我的一千行 PR，我现在就要合进生产环境。"**万一它比 CTO 能想出来的方案还好呢？**它确实可能更好。但那不代表它是"好的"——不代表 CTO 或公司会为这个结果高兴。
>
> 因为归根结底，**你做一件工作，价值不在于任何单个工作单元有多惊艳，而在于它能被规模化到一个团队、一个系统、一个组织里去。**

客户从 Basis 买的不是"史上最强报税表"，是**一致、可靠、可以被信任的东西**——就像对待一个人一样，信任逐步建立，权限逐步下放。

> 你不需要 Move 37。那东西在奥数竞赛里有用，在真实经济体的日常工作里没用。

这也重新定义了"自主"。Basis 说的自主，**不是**"点一下按钮、没人再看一眼"。恰恰相反，它更接近一个初级工程师或初级税务师交活的方式：不是甩给你一个一千行的 diff 说"信我，done 了"，而是**拆得清清楚楚的一叠小 PR，标明"我在这里做了一个重要的架构假设，理由是什么"**。

> 你要优化的不只是把活干完，还有**让审核你的人容易理解你做过的决策**。

这在软件工程里显然成立，在绝大多数专业领域里同样成立。

## 九、那些两年前还不存在的岗位

Basis 在招"语言架构师"和"agent 管理者"。这些岗位两年前根本不存在，他坦率承认还在摸索该怎么定义。

但有一件事他确定：**最重要的能力是系统思维。**

系统思维从哪来？来自那些必须设计某种抽象、并让它在极其多样的情况下都成立的经历。

优秀工程师当然算——但他补了一句：**历史上大部分工程工作其实并不是系统思维，而是执行导向的。**只有最难的那部分工程——设计系统形态、创造正确的抽象——才是。

而工程绝不是唯一的来源。他给了一个很妙的例子：**法律。**

> 我觉得美国的开国元勋们会是极好的 context engineer 或 agent 管理者。因为他们必须写下一段英文，而这段英文将在未来被律师和法官在运行时解释**数百万次**。
>
> 你在写一部法律时，你是在试图用英文写出一个**抽象层级恰到好处**的东西，让它覆盖整个情况空间。而且你必须对司法系统有心智理论，去预判他们会怎么解释它。

紧接着是那个关于脆弱规则的绝妙比喻：

> 机场的告示牌上写着"不得携带枪支、不得携带刀具、不得携带剑……"，你可以列出三十条，永远列不完。**要么列五十条脆弱的规则，要么写出那一条恰好完美覆盖一切的抽象。**

他还提到第三个来源：**那些维护过世界上最复杂 Excel 模型的人**，本质上做的是同一件事。

除此之外，Basis 还有一个叫 **Deployed Intelligence（部署智能）**的团队——他自称这个词是他们造的。它既不是 FDE（那种进场做定制开发的工程师），也不是那种"用 agent builder 帮你搭一个 agent"的所谓 agent PM。

**它是一群深刻理解这个职业本身的人。**他们的工作是帮会计师事务所完成向新时代的转型：不只是日常怎么用，而是这件事如何改变事务所的性质——能接什么样的业务、该招什么样的人、怎么变成那个所有人都想成为的"未来事务所"。

> 我们给了他们魔法。但如果不教他们怎么使用魔法，那就不算数。

## 十、护城河，与终将到来的苦涩教训

主持人问了两个最尖锐的商业问题，Mitch 的回答都毫不含糊。

**你们的 harness 工作会不会被模型吞掉？**

> 我假设它一定会被吞掉。我一点都不担心，这**绝对**就是未来。

他甚至指出，"规范不给 agent 看"这件事本身就是过渡态的证据——真正苦涩教训到来的那天，你不需要再做 context engineering，直接把想要的行为丢过去，它就会照做。至于多久：**大概率五年内，大概率不是两年内。**而 Basis 处在超高速扩张模式，**等不起苦涩教训**——他们要在通用能力到来之前把渗透做完。

**那么应用层公司未来是不是都得是 RL 实验室？**

> 如果现在有人在创业，我建议这样想：**技术护城河不是真的护城河。**Basis 的长期终局价值里，没有任何一部分来自某个别人没找到的 RL 秘方。

真正重要的是：他们现在确实最擅长构建可靠的长时程 agent，这让他们能拿下市场份额、深深嵌入客户的业务。**未来存在的护城河都会是商业护城河**——这在 AGI 时代成立，在前 AGI 时代同样成立。Salesforce 的护城河从来不是它能写出比你更好的 SQL，而是它的商业位置、它拥有的工作流、以及嵌入之后带来的一切。

**技术只是一次暂时的松动**，它让一家三年半前还不存在的公司，突然有机会去做这一切。

至于自我改进，Basis 内部的重点研究方向叫"闭环"（closing the loop）：从"agent 犯了个错"到"系统被改进了"的完整回路。他判断这个回路会闭合得相当快。原因是 agent 正在变成更好的 context engineer 和 harness engineer——尽管**目前它们设计 agent 系统的能力远远、远远差于设计普通软件**，因为这类工作太新，训练数据里几乎没有。

而这也解释了 behavior spec 更深一层的价值：**如果只有结果评估，信号极其稀疏**；行为规范提供的是密集得多的过程信号。至于这份信号最终是通过更新 harness 来生效（非正式 RL），还是通过更新权重来生效（正式 RL），在他看来是次要问题——**难的是造出好信号，那才是他们真正在做的事。**

## 尾声：不要被日更淹没

主持人请他给所有 AI 建设者一句建议，他说的是：

> 很容易看着这个世界觉得一切都在剧烈变化——推特上的注意力缺陷、中国实验室每天发布新东西——然后感到无力，觉得自己没法再做第一性原理的判断。
>
> 但如果你把这个新世界当作一次**底层范式转移**——就像当年的云计算那样——然后基于它去外推："既然有了这些东西，如果智能再强 X 倍会怎样，如果不再变强又会怎样"，你会构建出连贯得多的系统，做出好得多的战略下注，技术上和商业上都是。
>
> **事情在变，但范式没有在变**，至少没有变得那么剧烈。真正理解它，是在这个世界里建设的关键。

## 附：可直接迁移的十条

1. **给 agent 你能给的全部上下文**，别用给人看的方式压缩它。
2. **编程被攻克，靠的是运行时廉价验证 + 海量高质量数据**，可验证奖励只是起点——迁移时要迁移这三样。
3. **LLM 有巨大工作记忆、没有任何记忆。**超出窗口的一切，都要靠显式的笔记、子 agent、压缩来撑住。
4. **结果全对不等于过程可信。**100 条 eval 全过，仍可能是过拟合。
5. **把过程写成 behavior spec**：markdown、稀疏、只挑最重要的几条、**永远不给 agent 看**、判 true/false/na。
6. **规范与实现冲突时改实现**；模型变强后**主动退休规范**，总量应下降。
7. **Context 是运行时训练数据**，它比代码更影响性能，理应比代码更被珍视。
8. **确定你的组织正典**，像维护代码一样维护内部文档——删一段等于删一行代码。
9. **不要 Move 37。**客户买的是一致、可靠、可被逐步授权的信任。自主意味着"像初级同事那样交出可审阅的活"，不是"没人再看一眼"。
10. **技术护城河不是护城河。**在苦涩教训到来之前的窗口期里，把商业位置占住。
