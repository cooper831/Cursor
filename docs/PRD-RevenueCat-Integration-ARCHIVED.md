**术语表**


| 术语                          | 定义                                                               |
| --------------------------- | ---------------------------------------------------------------- |
| RevenueCat                  | 第三方应用内购买与订阅管理平台，提供统一 SDK 和后端 API 管理 IAP/GPB                      |
| IAP                         | Apple In-App Purchase，苹果应用内购买                                    |
| GPB                         | Google Play Billing，谷歌应用内计费                                      |
| Link-out                    | Apple 允许的外部支付链接跳转方式（StoreKit External Purchase Link Entitlement） |
| Entitlement                 | 权益。用户购买产品后获得的内容访问权限，是 RevenueCat 中权益管理的核心抽象层                     |
| Offering                    | RevenueCat 中的"产品展示方案"，可远程配置向用户展示的产品组合，无需发版                       |
| Package                     | Offering 中的"包"，每个 Package 包含一个跨平台产品（iOS SKU + Android SKU）       |
| Product / SKU               | 对应 App Store / Google Play 中的具体商品标识符                             |
| Non-consumable              | 非消耗型内购，一次购买永久拥有（如课程）                                             |
| Auto-renewable Subscription | 自动续期订阅，到期自动扣费续费（如存储服务月/年订阅）                                      |
| CustomerInfo                | RevenueCat SDK 返回的用户信息对象，包含该用户的全部权益状态                            |
| App User ID                 | RevenueCat 中标识用户的 ID，与品牌 App 统一账号体系的 User ID 一一对应                |
| Stripe                      | 第三方支付网关，Phase 2 用于 Link-out 网页支付                                 |
| Webhook                     | RevenueCat 向品牌后端推送购买/续订/退款等事件的 HTTP 回调机制                         |
| Receipt                     | 支付凭证。Apple/Google 在支付成功后返回的加密凭据，用于服务端验证                          |
| Sandbox                     | Apple/Google 提供的测试支付环境，不产生真实扣款                                   |

## 1. 项目背景与价值

### 1.1 公司与产品现状

我们是一个面向全球市场的母婴品牌，拥有原生 + React Native 双端（iOS / Android）App。主营实体母婴产品线涵盖背带、推车、暖奶器、餐椅、音响等品类，已在 Amazon、品牌独立站、App 内多渠道销售。

近期业务战略性拓展至**数字化内容领域**：

- **已上线**：瑜伽球视频课程（1 门），售价 $50，通过 Amazon 随球赠送 + 独立站单独购买
- **规划中**：存储订阅服务（按月/年自动续订），以及未来更多数字产品品类

### 1.2 当前痛点


| #   | 痛点                                                             | 影响                     | 严重度 |
| --- | -------------------------------------------------------------- | ---------------------- | --- |
| P1  | **渠道碎片化** — 课程购买散落在 Amazon 赠送、独立站购买两条链路，无统一管理                  | 运营效率低，用户权益难追踪          | 高   |
| P2  | **合规缺失** — App 内售卖数字产品必须遵循 Apple IAP / Google GPB 政策，当前无合规支付能力 | 无法在 App 内上架数字产品，存在下架风险 | 极高  |
| P3  | **订阅能力缺失** — 现有系统管理课程权益可用，但无法支撑订阅类产品（免费试用、自动续费、升降级、退款撤权）等复杂场景  | 无法上线订阅服务，业务受限          | 高   |
| P4  | **数据孤岛** — 已售课程用户数据与 App 用户体系割裂，无法在 App 内识别已购用户                | 用户体验断裂，复购率低            | 中   |
| P5  | **跨平台体验缺失** — iOS 用户购买后 Android 无法访问，反之亦然                      | 多设备用户流失                | 中   |


### 1.3 为什么选择 RevenueCat


| 评估维度   | RevenueCat 优势                             | 自建方案对比            |
| ------ | ----------------------------------------- | ----------------- |
| 合规支付   | 原生封装 StoreKit / GPB，自动处理 Receipt 验证       | 需自行对接两套 API，维护成本高 |
| 权益管理   | Entitlement 抽象层，一个权益可映射多平台多 SKU           | 需自建映射逻辑和同步机制      |
| 订阅生命周期 | 自动处理续费、过期、宽限期、账单重试                        | 需自行实现复杂状态机        |
| 跨平台同步  | 基于 App User ID 自动跨 iOS/Android 同步         | 需自建同步服务           |
| 数据分析   | 内置 MRR、流失率、试用转化等 Dashboard                | 需自建 BI            |
| 扩展性    | 支持 Stripe（Link-out）、A/B 测试、远程 Offering 配置 | 每个新功能都需开发         |
| 数据迁移   | REST API 支持 grant_promotional 批量授权        | 无标准方案             |
| 开发成本   | SDK 集成 1-2 周可上线                           | 自建预估 2-3 个月       |


### 1.4 项目价值

**对用户的价值：**

- 在 App 内直接购买数字内容，原生支付体验安全流畅
- 跨设备登录即可访问所有已购内容
- 已有购买记录无感迁移，无需重复付费

**对业务的价值：**

- 开辟 App 内数字产品营收新渠道，提升 LTV
- 合规支付解除 App 上架数字产品的政策风险
- 订阅模式创造可预测的经常性收入（MRR）
- RevenueCat Dashboard 提供实时收入与用户行为洞察

**对技术的价值：**

- 权益管理从自建迁移至成熟三方平台，降低维护成本
- 统一的 SDK 层抽象屏蔽 iOS/Android 支付差异
- Webhook + REST API 实现后端与支付系统的松耦合

#### 4.1.2 RevenueCat 业务模型架构

RevenueCat 使用三层抽象模型管理数字产品：

```
Layer 1: Entitlements（权益层）— 定义用户"能访问什么"
    │
    │   yoga_ball_course ─────── 解锁瑜伽球全部视频课程
    │   storage_pro ──────────── 解锁存储服务 Pro 全部功能
    │
    ▼
Layer 2: Products（产品层）— 定义"通过什么购买"，每个平台一个 SKU
    │
    │   yoga_ball_course_iap ─────── iOS IAP, $49.99, Non-consumable
    │   yoga_ball_course_gpb ─────── Android GPB, $49.99, One-time
    │   yoga_ball_course_stripe ──── Stripe, $49.99 (Phase 2)
    │
    │   storage_pro_monthly_iap ──── iOS IAP, TBD/月, Auto-renewable
    │   storage_pro_yearly_iap ───── iOS IAP, TBD/年, Auto-renewable
    │   storage_pro_monthly_gpb ──── Android GPB, TBD/月, Auto-renewable
    │   storage_pro_yearly_gpb ───── Android GPB, TBD/年, Auto-renewable
    │   storage_pro_monthly_stripe ─ Stripe, TBD/月 (Phase 2)
    │   storage_pro_yearly_stripe ── Stripe, TBD/年 (Phase 2)
    │
    ▼
Layer 3: Offerings（展示层）— 定义"用户看到什么"，支持远程配置
    │
    │   default (默认方案)
    │     ├── Package: yoga_ball_course（课程）
    │     ├── Package: storage_pro_monthly（存储月订阅）
    │     └── Package: storage_pro_yearly（存储年订阅）
    │
    │   [未来] experiment_pricing（A/B 测试方案）
    │     └── ... 不同价格组合 ...
    │
    ▼
App 客户端通过 getOfferings() 拉取展示层数据，渲染 UI
```

**层级关系规则：**

- 一个 Entitlement 可关联多个 Product（不同平台、不同支付方式的同一权益）
- 一个 Product 只属于一个 Entitlement
- 一个 Offering 包含多个 Package，每个 Package 对应一个跨平台产品
- 修改 Offering 不需要发版，RevenueCat Dashboard 即时生效

**课程购买后的权益开通流程（关键链路）：**

```
App 内 IAP/GPB 支付成功
    │
    ├──▶ 【即时·客户端主动调用】
    │     客户端调用现有后端课程权益接口
    │     POST {课程权益接口} { user_id, course_id, source: "iap", transaction_id }
    │     → 后端开放课程权限
    │     → 客户端收到成功响应 → 立刻解锁课程（无等待）
    │
    └──▶ 【异步·Webhook 自动推送】
          RevenueCat Webhook → 后端
          → 记录购买日志（用于对账和收入分析，非权益判断依据）
```

> **⚠️ 设计要点**：课程解锁不依赖 Webhook，而是由客户端在支付成功回调中**同步**调用现有后端接口完成。这确保了支付成功后用户零等待即可访问课程。

│  ├── BILLING_ISSUE → 标记账单问题, 告警     │
│  ├── REFUND → 撤销权益, 记录退款            │
│  ├── PRODUCT_CHANGE → 更新订阅档位         │
│  └── TRANSFER → 权益转移                   │
│                                          │
│  Step 5: 记录 event.id 为已处理            │
│                                          │
│  Step 6: 返回 200 OK                      │
└──────────────────────────────────────────┘
```

#### 4.2.6 Phase 2: Link-out 支付流程

```
用户在 App 内查看产品
    │
    ▼
展示合规的外部购买提示
(Apple External Purchase Link 要求的标准措辞)
    │
    ▼
用户点击"在网页购买"
    │
    ▼
跳转至品牌 Web 页面 (Stripe Checkout)
    │
    ├── URL 携带 app_user_id 参数
    │
    ▼
用户在网页完成 Stripe 支付
    │
    ▼
Stripe Webhook → RevenueCat
    │
    ├── RevenueCat 自动创建/更新 Subscriber
    ├── RevenueCat 自动授予对应 Entitlement
    │
    ▼
用户返回 App
    │
    ▼
App 调用 RevenueCat SDK 刷新 CustomerInfo
    │
    ▼
检测到新权益 → 解锁内容
```

// 课程权益 — 使用现有后端 API（接口格式待调研）
function hasCourseAccess(courseId: string): boolean {
    const courseEntitlements = getCachedCourseEntitlements();  // 来自现有后端
    return courseEntitlements.some(c => c.courseId === courseId && c.hasAccess);

**服务端验权实现（伪代码）：**

```
function verifyAccess(userId, productType, productId):

    if productType == "course":
        // 课程：直接查现有后端课程权益系统（唯一权威来源）
        return courseEntitlementService.checkAccess(userId, productId)

    if productType == "subscription":
        // 订阅：查本地 DB (Webhook 同步) + 可选 RC REST API
        localResult = db.query("SELECT active FROM user_entitlement
                                WHERE app_user_id = ? AND entitlement_id = ?",
                                userId, productId)

        if localResult.exists AND localResult.active:
            return GRANTED

        try:
            rcResult = revenueCatAPI.getSubscriber(userId)
            if rcResult.entitlements[productId].isActive:
                return GRANTED
        catch timeout/error:
            if localResult.exists:
                return localResult.active ? GRANTED : DENIED

        return DENIED
```

### 6.3 后端功能详述

#### F9: Webhook 接收与处理

**接口定义：**


| 项目           | 详情                                |
| ------------ | --------------------------------- |
| URL          | `POST /api/v1/revenuecat/webhook` |
| Content-Type | application/json                  |
| 认证方式         | Authorization Header（预共享 Token）   |


**需处理的事件类型：**


| 事件                      | 业务处理    | 本地数据操作                                                               | 备注                                          |
| ----------------------- | ------- | -------------------------------------------------------------------- | ------------------------------------------- |
| `INITIAL_PURCHASE` (课程) | 首次购买课程  | INSERT purchase_log（购买记录）                                            | ⚠️ **不用于权益开通**，课程权益由客户端同步调现有后端接口开通。此处仅做对账日志 |
| `INITIAL_PURCHASE` (订阅) | 首次订阅    | INSERT purchase_log; UPDATE user_entitlement SET active=true         | 订阅权益由 RC 管理，Webhook 同步至本地 DB                |
| `RENEWAL`               | 订阅续费    | INSERT purchase_log; UPDATE user_entitlement SET expires_at=new_date |                                             |
| `CANCELLATION`          | 用户取消续订  | UPDATE user_entitlement SET auto_renew=false, cancel_at=date         |                                             |
| `EXPIRATION`            | 订阅到期    | UPDATE user_entitlement SET active=false                             |                                             |
| `BILLING_ISSUE`         | 支付失败    | UPDATE user_entitlement SET billing_issue=true; 触发告警                 |                                             |
| `SUBSCRIBER_ALIAS`      | ID 别名映射 | UPDATE user_alias_mapping                                            |                                             |
| `REFUND` (课程)           | 课程退款    | INSERT refund_log; **通知现有课程权益系统撤销权限**                                | 退款需联动课程权益系统                                 |
| `REFUND` (订阅)           | 订阅退款    | UPDATE user_entitlement SET active=false; INSERT refund_log          |                                             |
| `PRODUCT_CHANGE`        | 升降级     | UPDATE user_entitlement SET product_id=new_product                   |                                             |
| `TRANSFER`              | 权益转移    | 更新 old_user 和 new_user 的权益记录                                         |                                             |


**安全 & 可靠性：**


| 要求   | 实现方式                                                |
| ---- | --------------------------------------------------- |
| 认证   | 比对请求 Header 中的 Authorization 与预配置 Token             |
| 幂等   | 以 event.id 为唯一键，INSERT 前检查 processed_events 表       |
| 重试兼容 | RevenueCat 重试间隔为 5s → 10s → 30s → 1min → 5min → ... |
| 超时   | 接口响应 ≤ 5s，超时 RevenueCat 会重试                         |
| 响应码  | 成功返回 200；认证失败返回 401；处理异常返回 500（触发重试）                |


#### F10-F11: 购买记录与权益查询 API

**这些是品牌后端自建的 API，提供给客户端和内部服务调用。数据不是直接从 RevenueCat 透传，而是通过 Webhook 同步到本地数据库后，由后端 API 统一加工返回。**

**数据流架构：**

```

│                         数据写入链路                                      │
│                                                                          │
│  用户在 App 内购买/续费/退款/过期                                           │

│       ▼                                                                  │
│  Apple/Google 处理 → RevenueCat 验证                                      │
│       │                                                                  │
│       ▼                                                                  │
│  RevenueCat 发送 Webhook ──▶ 品牌后端 Webhook 端点 (F9)                    │
│       │                                                                  │
│       ▼                                                                  │
│  后端解析事件 → 写入本地数据库                                               │

│       └── user_subscription 表（用户当前订阅状态）                           │

└──────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────┐
│                         数据读取链路                                      │
│                                                                          │
│  客户端 App / 内部服务 ──请求──▶ 品牌后端 API (F10-F11)                     │

**为什么不直接调 RevenueCat REST API 透传给客户端？**


| 原因     | 说明                                                       |
| ------ | -------------------------------------------------------- |
| 数据加工需求 | RC 返回的 subscriber 原始数据结构不适合直接展示：缺少订单号、金额展示格式、产品名称等，需后端加工 |
| 数据补充需求 | 迁移用户的购买来源（Amazon/独立站）、原始订单号等信息只存在于品牌本地数据库，RC 中无此信息       |
| 性能     | 本地数据库查询 <50ms，调 RC REST API 额外增加 200-500ms 网络延迟          |
| 限流     | RevenueCat REST API 有请求频率限制（120 req/min），高并发时可能被限流       |
| 解耦     | 后端 API 作为抽象层，客户端不依赖 RC 数据结构，便于后续切换或扩展数据来源                |


**各 API 的数据来源与用途说明：**


| API                                  | 方法  | 数据来源                                                | 调用方                        | 用途                                                |
| ------------------------------------ | --- | --------------------------------------------------- | -------------------------- | ------------------------------------------------- |
| `/api/v1/user/{userId}/entitlements` | GET | **混合来源**：课程权益从现有课程权益系统查询，订阅权益从本地 DB (Webhook 同步) 查询 | 内部服务（如视频流分发服务验权）、客户端（补充场景） | 聚合课程+订阅权益的统一视图。**客户端日常判断：课程走现有后端 API，订阅走 RC SDK** |

#### F12: 数据迁移脚本

**脚本规格：**


| 项目  | 详情                                                                                                        |
| --- | --------------------------------------------------------------------------------------------------------- |
| 语言  | Java（与现有后端技术栈一致）或 Python                                                                                  |
| 输入  | CSV 文件（app_user_id, purchase_source, purchase_date, order_id）                                             |
| API | RevenueCat REST API: `POST /v1/subscribers/{app_user_id}/entitlements/{entitlement_id}/grant_promotional` |
| 参数  | `{ "duration": "lifetime" }`                                                                              |
| 认证  | RevenueCat Secret API Key（Header: `Authorization: Bearer {secret_key}`）                                   |
| 并发  | 单线程顺序执行（≤100 条，无需并发优化）                                                                                    |
| 重试  | 失败自动重试 3 次，间隔 2s/5s/10s                                                                                   |
| 输出  | 迁移报告：总数 / 成功 / 已存在 / 失败 + 失败明细                                                                            |


#### F13: 退款处理

退款由 Apple/Google 侧发起 → RevenueCat 接收 → Webhook 推送 REFUND 事件 → 后端处理：

1. 撤销对应 Entitlement（RevenueCat 已自动处理，后端同步本地状态）
2. 写入 refund_log 表
3. 用户下次打开 App 时 SDK 自动拉取最新 CustomerInfo，权益已撤销

#### F14: 现有课程权益系统对接（保留而非下线）

> **架构决策变更**：现有课程权益系统**不会下线**，而是继续作为课程权益的唯一权威来源运行。App 内课程购买成功后，需要对接该系统完成权益开通。

**对接方案：**


| 步骤  | 操作                                   | 验证         |
| --- | ------------------------------------ | ---------- |
| 1   | 调研现有课程权益接口格式和鉴权方式                    | 接口文档 ready |
| 2   | 客户端在 RC SDK 购买成功回调中，集成对现有后端权益接口的调用   | 购买后课程即时解锁  |
| 3   | 实现客户端重试机制（3次重试 + App 启动补偿）           | 弱网场景权益不丢失  |
| 4   | Webhook 中课程退款事件联动现有系统撤销权限            | 退款后课程被锁    |
| 5   | 验证全渠道（App IAP + Amazon + 独立站）权益数据一致性 | 各渠道用户权益正确  |


**待调研事项（⚠️ 需开发团队确认）：**

- 现有课程权益查询接口的 URL、请求/响应格式
- 现有课程权益开通接口的 URL、请求参数（user_id, course_id, source, transaction_id?）
- 接口鉴权方式（JWT / API Key / 内部调用无需鉴权？）
- App 当前如何判断课程是否已购？是调接口还是读本地状态？
- 现有系统是否有撤销权限的接口（用于退款联动）？

## 8. 非功能需求

### 8.1 性能要求


| 指标           | 目标值           | 测量方式                        |
| ------------ | ------------- | --------------------------- |
| SDK 初始化      | ≤ 2s（冷启动）     | App 启动到 SDK configure 完成    |
| Offerings 加载 | ≤ 1s          | getOfferings() 调用到返回        |
| 购买流程端到端      | ≤ 10s         | 点击购买到权益激活（含原生支付面板时间除外）      |
| 权益验证（在线）     | ≤ 500ms       | getCustomerInfo() 到返回       |
| 权益验证（缓存）     | ≤ 50ms        | 本地 CustomerInfo 缓存命中        |
| Webhook 处理   | ≤ 5s          | 从 HTTP 请求接收到 200 响应         |
| 后端 API 响应    | ≤ 200ms (P99) | /entitlements, /purchases 等 |


### 8.2 可用性与可靠性


| 指标                | 目标值                                                                     |
| ----------------- | ----------------------------------------------------------------------- |
| RevenueCat 服务 SLA | 依赖 RevenueCat 官方 99.95%                                                 |
| 后端 Webhook 端点可用性  | 99.9%                                                                   |
| 降级策略              | RevenueCat 不可用时，客户端使用 SDK 本地缓存（最近一次 CustomerInfo）；后端使用 Webhook 同步的本地数据库 |
| 离线能力              | 基于本地缓存权益 + 已下载课程视频，离线可继续观看                                              |
| 数据一致性             | 最终一致（Webhook 事件延迟 ≤ 30s）                                                |


### 8.3 安全要求


| 维度            | 要求                                                 |
| ------------- | -------------------------------------------------- |
| 通信加密          | 全链路 HTTPS，TLS 1.2+                                 |
| Webhook 认证    | 验证 RevenueCat Authorization Header Token           |
| API Key 分级管理  | Public Key（客户端 SDK，可暴露）vs Secret Key（服务端 API，绝不暴露） |
| Secret Key 存储 | 通过环境变量或密钥管理服务注入，不得硬编码在代码中                          |
| Receipt 验证    | 服务端验证（RevenueCat 自动处理），客户端不做 receipt 解析            |
| 支付信息          | 品牌侧不存储任何用户支付卡号信息，全部由 Apple/Google/Stripe 托管        |
| 权限最小化         | RevenueCat Service Account 权限遵循最小化原则               |

| R8  | **Webhook 丢失或延迟** — 后端未及时收到购买/退款事件                | 本地数据与 RC 不一致    | 低   | 中   | 1) RevenueCat 自动重试机制；2) 定期对账脚本（RC API vs 本地 DB）；3) 关键操作以 SDK CustomerInfo 为准，后端为辅                                | 后端                 |
| R9  | **课程权益开通失败** — IAP 支付成功但调现有后端接口开通权限失败             | 用户付款但无法访问课程     | 低   | 高   | 1) 客户端自动重试（3次）；2) App 启动时补偿检查（RC 有购买记录但课程未开通则重新调用）；3) Webhook 兜底触发开通；4) 客服手动处理通道                                 | 客户端 + 后端           |
| R10 | **混合权益架构一致性** — 课程(现有系统) 和 订阅(RC) 两套系统数据不一致       | 用户看到矛盾的权益状态     | 低   | 中   | 1) 客户端并行查询两个系统，分区展示；2) 课程退款 Webhook 联动现有系统撤权限；3) 定期对账                                                            | 后端                 |

### B. Apple 审核 Checklist

- 全部数字内容/服务使用 IAP 支付（Guidelines 3.1.1）
- 订阅页展示自动续费价格、周期、免费试用时长
- 订阅页展示标准合规措辞（见 8.4 节模板）
- 提供 "Manage Subscriptions" 链接至 Apple 订阅管理
- 提供 "Restore Purchases" 按钮且功能正常
- 展示 Terms of Service 和 Privacy Policy 链接
- Privacy Policy 中包含 RevenueCat 作为数据处理方的说明
- App 内不展示非 IAP 的购买入口（Phase 1）
- 非消耗品（课程）不提供重复购买入口

### C. Google Play 审核 Checklist

- 全部数字内容/服务使用 GPB 支付
- 使用 Google Play Billing Library 最新稳定版
- 订阅页展示定价和条款
- 应用内提供取消订阅的路径说明
- 在 Google Play Console 正确配置 Service Account 权限
